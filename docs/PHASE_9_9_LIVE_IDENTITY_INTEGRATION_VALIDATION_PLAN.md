# Phase 9.9 Live Identity Integration Validation Plan

Status: PLANNING ONLY

Branch: phase-9-identity-platform

## Objective

Phase 9.9 proves that the Phase 9 identity platform works with real external identity providers and realistic enterprise identity flows in staging. This phase validates live integrations only. It does not add new identity features, activate production credentials, deploy production, modify DNS, or start Phase 9.10.

Phase 9.8 proved controlled implementation security. Phase 9.9 validates real-world provider behavior, callback handling, MFA devices, SCIM provisioning, operational recovery, and security evidence collection.

## Safety Boundary

Allowed:

- Staging-only provider applications.
- Staging-only OAuth, SSO, SCIM, and MFA validation.
- Staging-only test accounts.
- Staging-only secrets.
- Documentation of failures and fixes.

Forbidden:

- Production OAuth credentials.
- Production SAML certificates.
- Production SCIM tokens.
- Production MFA encryption keys.
- Production DNS changes.
- Production deployments.
- Customer traffic.
- Phase 9.10 freeze work.
- Phase 10 work.

## Environment Separation

Development:

- Local Next.js control plane.
- Local or disposable database.
- Mock identity providers and deterministic tests.
- No live customer data.

Validation/Staging:

- `https://staging-console.uzyntra.com`
- Disposable or staging Supabase database.
- Staging Google OAuth app.
- Staging GitHub OAuth app.
- Staging enterprise IdP tenant/app.
- Staging SCIM client.
- Staging-only MFA test users.

Production:

- No Phase 9.9 credentials.
- No Phase 9.9 provider apps.
- No staging OAuth/SSO/SCIM secrets.
- No customer identity traffic until production launch approval.

Rules:

- Store live staging secrets only in the staging provider environment.
- Do not commit secrets.
- Do not paste secrets into documentation.
- Do not reuse validation secrets for production.
- Rotate any staging secret that appears in logs or terminal history.
- Record only secret names and provider references.

## 1. Google OAuth Staging Validation

Setup:

- Create a dedicated staging Google OAuth client.
- Configure callback:
  - `https://staging-console.uzyntra.com/api/auth/oauth/google/callback`
- Add only approved staging test users to the OAuth consent screen.
- Enable Google provider only in staging.

Positive tests:

- Start Google login from staging.
- Complete login with verified Google email.
- Confirm session creation.
- Confirm organization selection.
- Confirm external identity linked.
- Confirm identity audit event created.
- Confirm OAuth login attempt marked completed.

Negative tests:

- Callback replay is rejected.
- Invalid state is rejected.
- Expired state is rejected.
- Invalid PKCE verifier is rejected.
- Incorrect redirect URI is rejected by provider or application.
- Provider disabled state blocks login.
- Revoked OAuth consent fails safely.
- Unverified email is rejected.
- Duplicate external subject cannot link to another account.

Success criteria:

- Google login works for staging test users only.
- No tokens or authorization codes appear in logs.
- No provider secret is returned by APIs.
- Account-linking behavior is deterministic and tenant-safe.

## 2. GitHub OAuth Staging Validation

Setup:

- Create a dedicated GitHub OAuth App for staging.
- Configure callback:
  - `https://staging-console.uzyntra.com/api/auth/oauth/github/callback`
- Enable GitHub provider only in staging.

Positive tests:

- Complete GitHub login.
- Confirm session creation.
- Confirm external identity linked.
- Confirm verified primary email is used.
- Confirm audit events and login attempt state.

Negative tests:

- Missing public email is handled through verified email lookup if supported.
- Unverified email is rejected.
- Callback replay is rejected.
- Invalid state is rejected.
- Invalid PKCE verifier is rejected.
- External subject collision is rejected.
- Disabled GitHub provider blocks login.

Success criteria:

- GitHub login works for approved staging test users.
- Missing/unverified email cases fail safely.
- No GitHub token or provider secret leaks.

## 3. Enterprise SAML Validation

Recommended provider:

- Okta Developer or Microsoft Entra ID.

Setup:

- Create a staging SAML application.
- Configure ACS URL:
  - `https://staging-console.uzyntra.com/api/auth/sso/saml/<provider>/callback`
- Configure SP Entity ID:
  - `https://staging-console.uzyntra.com`
- Configure NameID/email claim mapping.
- Import IdP metadata or certificate into staging configuration.
- Enable provider for a staging organization only.

Positive tests:

- SAML login starts successfully.
- IdP redirects to ACS.
- Assertion signature is present and accepted.
- Issuer validation passes.
- Audience validation passes.
- Email/domain mapping passes.
- Session creation succeeds.
- Identity audit event is created.

Negative tests:

- Replay the same SAML response.
- Modify audience.
- Modify issuer.
- Use expired assertion.
- Use assertion before `NotBefore`.
- Remove signature when signature is required.
- Use disallowed email domain.
- Use provider from wrong organization.

Success criteria:

- Real SAML login succeeds with staging IdP.
- Replay and manipulation tests are rejected.
- No SAML private material or full assertion payload is logged.

## 4. Enterprise OIDC Validation

Recommended provider:

- Microsoft Entra ID, Okta Developer, or Auth0.

Setup:

- Create staging OIDC application.
- Configure callback:
  - `https://staging-console.uzyntra.com/api/auth/sso/oidc/<provider>/callback`
- Configure issuer, client ID, client secret reference, scopes, and allowed domains.
- Enable provider for a staging organization only.

Positive tests:

- OIDC login starts.
- State and PKCE challenge are generated.
- Provider callback completes.
- ID token issuer validates.
- Audience/client ID validates.
- Email verification validates.
- Session creation succeeds.
- Audit event is created.

Negative tests:

- Invalid state.
- Expired state.
- Invalid PKCE verifier.
- Wrong issuer.
- Wrong audience.
- Expired token.
- Unverified email.
- Disallowed domain.
- Provider disabled.

Success criteria:

- Real enterprise OIDC login succeeds.
- State, PKCE, issuer, audience, expiry, and claim checks are enforced.
- Client secret remains provider-environment only.

## 5. SCIM Provisioning Validation

Setup:

- Configure staging SCIM provider in UZYNTRA.
- Generate a staging SCIM token.
- Configure SCIM base URL:
  - `https://staging-console.uzyntra.com/scim/v2`
- Configure token in the external SCIM client.
- Use only staging test users/groups.

User tests:

- Create user.
- Update user.
- Disable user.
- Delete or deprovision user.

Group tests:

- Create group.
- Update group.
- Change membership.
- Delete/deprovision group.

Negative tests:

- Invalid token.
- Revoked token.
- Expired token.
- Cross-tenant token use.
- Disabled SCIM provider.
- Privileged role escalation through unmapped group.
- Malformed SCIM payload.

Success criteria:

- Provisioning writes correct staging organization records.
- Deprovisioning behavior is safe and auditable.
- Group mapping does not grant unintended privileges.
- SCIM token value is never stored or displayed after creation.
- SCIM events and sync state are visible in identity observability.

## 6. Real MFA Device Validation

TOTP devices:

- Google Authenticator.
- Microsoft Authenticator or 1Password.

WebAuthn devices:

- Chrome passkey.
- Windows Hello or hardware key if available.

Positive tests:

- Enroll TOTP.
- Verify TOTP.
- Generate recovery codes.
- Complete MFA login challenge.
- Register WebAuthn/passkey if supported.
- Verify MFA audit events and observability signals.

Negative tests:

- Wrong TOTP code.
- Expired MFA challenge.
- Replay completed challenge.
- Reuse recovery code.
- Unauthorized MFA method deletion.
- Lost-device recovery workflow.
- Admin-assisted recovery workflow.

Success criteria:

- MFA works with real devices.
- Recovery codes are single-use.
- MFA reset/recovery is audited and permission-gated.
- No TOTP secret, WebAuthn private material, or recovery-code value appears in logs.

## 7. Identity Disaster Recovery Drill

Drill scenarios:

- Accidental OAuth provider disable.
- Broken SSO configuration.
- Locked admin account.
- Lost MFA device.
- SCIM token compromise.
- Break-glass account activation.
- Audit evidence recovery.

For each drill document:

- Incident.
- Impact.
- Detection signal.
- Recovery steps.
- Time to recover.
- Audit evidence.
- Follow-up hardening.

Success criteria:

- Operators can recover without database surgery.
- Break-glass access is time-bound, MFA-required, and audited.
- SSO misconfiguration does not permanently lock all administrators out.
- Recovery evidence is sufficient for a customer/security review.

## 8. Production Configuration Separation

Before any production launch:

- Create production provider apps separately from staging.
- Create production Supabase separately from validation/staging.
- Generate production secrets separately.
- Keep staging and production redirect URIs separate.
- Never promote staging OAuth/SSO/SCIM secrets to production.
- Document all production variable names without values.

Production must not contain Phase 9.9 test credentials.

## 9. Security Evidence Collection

Collect:

- Login attempt evidence.
- Audit event IDs.

- SCIM event IDs.
- MFA challenge/recovery audit evidence.

## Rollback Plan

If live validation fails:

1. Disable the affected staging provider.
2. Revoke or rotate provider credentials if leakage is suspected.
3. Revoke staging SCIM tokens if provisioning fails unsafe.
4. Clear only temporary staging test records.
5. Preserve audit evidence of the failure.
6. Document the defect and stop before Phase 9.10.

No production rollback should be required because production resources are not touched in Phase 9.9.
